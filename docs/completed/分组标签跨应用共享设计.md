## 🎯 背景与目标

当前 Trae / Buddy(B) / Qoder(Q) 三个应用各自维护独立的账号分组体系，互不可见；积分看板只能整池聚合查看；API Key 只能按「精确账号白名单」约束调度。四个需求归纳为一句话：

**把「分组」「标签」从各应用私有数据升级为跨应用共享的组织维度，并让看板、资源调度、API Key 三个消费方都能按这两个维度过滤。**

依赖关系：

```
需求①分组共享 ──┬──> 需求②看板筛选
                │
需求③标签体系 ──┴──> 需求④调度/API Key 绑定
```

## 🏗️ 总体设计

### 核心原则

1. **定义共享、归属分池**：分组/标签的「定义」（名称、颜色、排序）全局唯一一份；「成员关系」按池保持各自现有机制（Trae 走映射表，WB/Qoder 走账号字段）。
2. **uid 命名空间不冲突** 是共享的前提，新增任何绑定表都以 `(pool 无关的 uid)` 为键，不做第二套命名。
3. **serde default 兼容**：所有新增字段对旧数据零破坏（沿用项目惯例）。
4. **变更联动热重载**：分组/标签/成员关系变化时，若网关运行中则 `reload_pools_if_running`（对齐 `qoder_account_move` 惯例）。

### 新数据模型

```
Tag { id, name, color, order }            // 与 Group 同构，id 前缀 tag_
account_tags 表（行文档）: pk = uid, data = ["tag_id", ...]   // 多对多，跨池一张表
```

分组定义统一收敛到既有 `groups` 行文档表（每行一个 Group JSON）；`group_members` 表语义收窄为「仅 Trae 池成员关系」。

### 📌 关键决策（ADR 摘要）

| # | 决策 | 理由 | 代价 / 拒绝的替代方案 |
|---|---|---|---|
| D1 | 分组定义统一入 `groups` 表；成员关系**保持各池现状**，不做全局统一 membership | WB/Qoder 成员落在账号字段，导入/导出天然携带；统一映射表需双向同步，风险大于收益 | 代价：成员关系机制两套并存（内部实现细节，前端无感）。拒绝「全量统一 membership」 |
| D2 | 迁移时同名分组自动合并为一条，**全部统一重新生成 `shg_` 新 ID**，不保留任何原应用 ID，引用按 id_map 全量重定向 | 同名即同组是用户直觉；统一新 ID 后 id 前缀单一、后续逻辑无需兼容三套前缀 | 拒绝「保留旧 id」：共享后 id 体系混杂三套前缀，长期维护成本高。已确认（2026-10-10） |
| D3 | 标签绑定存独立 `account_tags` 表，不塞进各池账号结构 | 三池账号结构各改一遍 + 导入导出格式膨胀，成本高；独立表 uid 天然跨池，多对多语义清晰 | 代价：账号导入/导出需补 tags 字段读写（**确认要做**，见 P2）。拒绝「账号字段存 Vec<tag_id>」 |
| D4 | API Key 的分组/标签约束**运行时实时展开**（带缓存），不落盘为账号快照 | 分组成员变化即时生效，无需改 key/重启；符合「绑定组织维度而非具体账号」的产品意图 | 代价：请求路径多一次缓存查询（复用 config_cache 模式）。拒绝「创建 key 时展开快照」 |
| D5 | 交集语义统一：**池筛选（调度页）= 组 ∩ 标签**；**Key 授权 = 精确白名单 ∪ (组 ∩ 标签)**——组与标签两维度间取交集，单一维度勾选时退化为该维度成员集 | 两处「组+标签组合」语义一致（既属于这些组、又带这些标签），UI 文案统一不歧义 | 交集仅在两维度均非空时生效；均空 = 该 key 不受组/标签限制。已确认（2026-10-10） |

## 🔧 详细设计

### 一、需求①：分组定义跨应用共享

#### 存储

- 统一读写新函数（[store/docs.rs](file:///d:/code/AIWorkAssistant_main/src-tauri/src/store/docs.rs)）：
  - `group_defs_load(s) -> Vec<Group>`：仅读 `groups` 表定义行（不再附带 membership）
  - `group_defs_save(s, defs)`：全删全写定义行，**不触碰 `group_members` 表**
- 现有 `groups_load/groups_save` 保留供 Trae 命令内部使用（定义部分改走新函数，避免双写）。

#### 命令层

新增统一命令（建议放 `commands/accounts.rs` 或新文件 `commands/shared_groups.rs`）：

| 命令 | 行为 |
|---|---|
| `shared_groups_list()` | 读统一 defs；`count/uids` 需要池上下文时由各池既有 list 组装（见下） |
| `shared_groups_create(name, color)` | 全局重名校验（推广 qoder `validate_name`）；id 前缀统一 `shg_` |
| `shared_groups_update(id, ...)` | 同上 |
| `shared_groups_delete(id)` | 删除定义 + 三池成员回落「未分组」（Trae 清 group_members 行；WB/Qoder 清账号 group_id 字段）+ 清理 `api_pool.group_ids/wb_group_ids/qoder_group_ids` 与 `api_keys.allowed_groups` 引用 + 热重载 |

改造三池既有 list 命令（`groups_list` / `workbuddy_groups_list` / `qoder_groups_list`）：

- 签名与返回结构 `GroupView` **不变**（前端零改动即可看到共享分组）；
- 内部：defs 改读统一存储，uids 仍从各自池推导。
- create/update/delete 改为转发统一命令（保留旧命令名作薄封装，避免破坏既有前端调用点）。

#### 数据迁移（启动一次性，SCHEMA_VERSION bump 或惰性迁移）

```
1. 读三处 defs：groups 表行 + kv("workbuddy_groups") + kv("qoder_groups")
   → 迁移前整体快照至 kv("groups_pre_migration") 备份键
2. 按 name 去重合并（同名合并为一条，颜色取 Trae > Buddy > Qoder 首个出现的定义），
   逐条生成统一新 ID（shg_ + 时间戳 + 4 位随机 hex），构建 id_map{全部旧 id → shg_ 新 id}
   —— 不区分「保留/合并」，旧 id（g_/wbg_/qoderg_）一律重定向，不保留
3. id_map 全量重定向：
   - group_members 表的 group_id（Trae membership）
   - WB 账号 group_id 字段（读-改-写罩 wb_pool_lock）
   - Qoder 账号 group_id 字段（读-改-写罩 qoder_pool_lock）
   - api_pool.group_ids / wb_group_ids / qoder_group_ids
4. 全删全写 groups 表（新 defs，id 均为 shg_ 前缀）
5. 删除 kv("workbuddy_groups")、kv("qoder_groups")
6. 标记 kv("unified_groups_migrated")，二次启动幂等跳过
```

边界场景：同一池内历史上存在两个同名分组（Trae/Buddy 无重名校验）时，二者成员合并到同一条新分组——符合「同名即同组」语义；若合并后组内账号数异常，用户可在共享分组中拆分重建。

#### 前端改动（极小）

- 三池账号页的 GroupsModal / GroupSelect 不变（命令返回结构未变）。
- 可选增强：分组名旁加池来源徽标（该组在哪些池有成员）。

### 二、需求②：积分看板顶部分组/账号筛选

#### UI

- 位置：Dashboard 页面工具行（数据源切换、刷新旁），**平台视图内全局生效**（KPI 行、积分统计、到期日历、Token 统计全部联动）。
- 控件：
  - 分组多选下拉（chips 展示，含「全部分组」清空态）
  - 账号多选下拉（候选随分组筛选联动：选中分组后仅列组内账号；也可直接全量搜账号）
  - 筛选状态持久化到本平台视图（内存即可，P1 不做 localStorage）

#### 数据流

```
Dashboard(平台实例)
  ├─ accounts(本平台全量) ──filter──> visibleAccounts ──> KpiRow / CreditsTab / ExpiryTab / TokensTab
  └─ 分组下拉数据源 = 本池 groups_list().GroupView{id, name, uids}
       （共享分组生效后自动包含其他应用创建的分组）
```

- 分组→账号解析直接复用 `GroupView.uids`，**前端无需新增后端命令**。
- 网关/官网消耗明细的账号级过滤：按明细数据携带的 uid 字段过滤；无 uid 维度的数据点（部分官网聚合口径）不做静默截断，显示「该数据源不支持账号级筛选」徽标（对齐 CreditsTab 现有三源口径不做静默合并的原则）。

### 三、需求③：账号标签体系

#### 存储与命令

- `tags` 行文档表（DDL 追加进 [schema.rs](file:///d:/code/AIWorkAssistant_main/src-tauri/src/store/schema.rs)，`ROW_TABLES` 白名单同步登记）；
- `account_tags` 行文档表：`pk = uid`（跨池全局唯一），`data = Vec<tag_id>`；
- 命令（新文件 `commands/tags.rs`）：

| 命令 | 行为 |
|---|---|
| `tags_list()` | `TagView{id, name, color, order, count, uids}`，uids 从 account_tags 反查 |
| `tags_create/update/delete` | 全局重名校验；delete 时清理 account_tags、`api_keys.allowed_tags`、`api_pool.*_tag_ids` 引用 + 热重载 |
| `account_tags_set(uid, tag_ids[])` | 全量覆盖式设置（前端多选框一次性提交）；校验 tag_id 存在 |
| `account_tags_map()` | 一次返回 `HashMap<uid, tag_ids>`（各池账号列表组装时联表用，避免 N+1 invoke） |

#### 账号视图扩展

- Trae `AccountView`、WB 账号视图、Qoder 账号视图各加 `tags: Vec<String>`（serde default），在各自 list 命令组装时从 `account_tags_map()` 填充；**不改账号持久化结构**（D3）。

#### 导入/导出携带标签（已确认要做）

- 导出：三池账号导出格式各加可选 `tags: Vec<String>`（tag id 数组，serde skip_serializing_if 空），导出时从 `account_tags` 表填充；
- 导入：读到 tags 字段时写入 `account_tags` 表（uid 键跨池通用）；导入的 tag id 不存在时忽略该 id（不自动创建标签，避免导入方标签体系污染本机）；
- 导出文件不携带标签定义本身——标签定义属全局数据，导入方以本机标签体系为准，仅恢复「uid ↔ tag id」绑定。

#### 前端

- 通用组件（`src/pages/accounts/TagSelect.tsx`、`TagsModal.tsx`，复用 GroupsModal 模式）；
- 三池账号页：行内标签 chips（最多显示 2 + N）+ 编辑弹框多选；
- 语义：分组 = 单选归属（不变）；标签 = 多选标注，两者正交。

### 四、需求④：资源调度与 API Key 按分组/标签筛选

#### 调度池筛选（资源调度页）

- [ApiPoolFile](file:///d:/code/AIWorkAssistant_main/src-tauri/src/models.rs#L602) 新增字段（serde default）：

```
trae_tag_ids / wb_tag_ids / qoder_tag_ids : Vec<String>   // 各池标签筛选；空 = 不限
```

- 调度同步（`reload_pools` / 各池 sync）时：标签→uids 由 `account_tags` 反查展开，与分组筛选取**交集**（D5，均空 = 不限）。
- 联动：账号打标签/换分组/删标签时热重载（对齐现有分组联动）。
- 资源调度页 UI：三池分组筛选 chips 旁补标签筛选 chips。

#### API Key 绑定（跨应用调度）

- [ApiKeyEntry](file:///d:/code/AIWorkAssistant_main/src-tauri/src/api_server/api_keys.rs#L205-L246) 新增字段（serde default）：

```
allowed_groups : Vec<String>   // 共享分组 id；空 = 不通过该维度限制
allowed_tags   : Vec<String>   // 共享标签 id
```

- 展开逻辑（`pool_constraints()` 内，D4/D5）：

```
group_set   = 展开_allowed_groups（三池组内成员，按池生成 trae:/buddy:/裸uid）
tag_set     = 展开_allowed_tags
cross_set   = 两者均非空 → group_set ∩ tag_set（交集）
              仅一方非空 → 非空的一方
              均空      → 不参与约束
effective_allowed = allowed_accounts（精确白名单，含池前缀）∪ cross_set
schedule_mode=dedicated：专一账号语义不变，优先级最高，不受组/标签影响
```

- 展开数据源：groups 表 + group_members/账号 group_id + account_tags，经 `config_cache` 缓存（分组/标签/成员任何写路径触发失效），避免每请求查库。
- 语义对齐现有混合白名单：展开的 uid 带池前缀参与 `split_pool_tagged` 作用域判定，天然实现「一个 key 绑定跨三池的分组」。
- 前端 [ApiKeysManager.tsx](file:///d:/code/AIWorkAssistant_main/src/components/api/ApiKeysManager.tsx)：
  - 创建/编辑表单新增「分组」「标签」多选（候选来自统一 list + 各池成员计数）；
  - key 列表展示「覆盖账号数」预览（实时展开计算）；
  - 文案明确交集语义（D5）：「分组与标签同时勾选时，取同时满足两者的账号」。

## 🗓️ 分期实施计划

### P0 — 分组统一共享（需求①）

- `group_defs_load/save` + 统一命令 + 三池 list 转读统一 defs + 迁移（统一 `shg_` 新 ID + id_map 全量重定向）+ 迁移单测
- **验收**：Trae 新建分组在 Buddy/Qoder 账号页可见可选；迁移后所有分组 id 均为 `shg_` 前缀，旧 id（`g_/wbg_/qoderg_`）引用零残留（group_members、账号 group_id、api_pool 筛选均正确重定向）；`workbuddy_groups`/`qoder_groups` kv 清除且二次启动幂等；备份键 `groups_pre_migration` 可回滚。

### P1 — 看板顶部筛选 + 标签体系（需求②③）

- Dashboard 顶部筛选栏（分组/账号多选）+ visibleAccounts 管线 + 数据源不支持筛选的提示徽标
- tags / account_tags 表 + 命令 + 三池账号视图 tags 填充 + TagSelect/TagsModal + 账号页标签维护
- **验收**：筛选后 KPI/积分/到期/Token 全联动；官网源不支持账号过滤时给出明确提示；标签在任一应用设置、三池账号均可选同一标签；删除标签后所有引用清理干净。

### P2 — 调度与 API Key 绑定（需求④）

- ApiPoolFile 标签筛选字段 + 展开与热重载 + 调度页 UI
- ApiKeyEntry allowed_groups/allowed_tags + config_cache 缓存展开（组∩标签交集）+ ApiKeysManager 表单
- 三池账号导入/导出携带 tags 字段（导出填充 + 导入恢复绑定）
- **验收**：key 绑定分组后，新加入该分组的账号无需改 key 即被纳入调度；组+标签同时勾选时仅放行同时满足两者的账号（交集）；组/标签删除后 key 约束自动收窄不悬空；导出→导入到另一环境后标签绑定完整恢复。

## ✅ 已确认决策（2026-10-10）

1. **迁移同名合并策略**：同名自动合并，**不保留原应用数据，统一使用新 `shg_` ID**，旧 id 全量重定向（D2）。
2. **key 组/标签语义**：**交集**——组与标签同时勾选时放行「既属于所选组、又带所选标签」的账号（D5）。
3. **账号导出携带标签**：确认要做，导出格式加 `tags` 字段，导入恢复绑定（见需求③「导入/导出携带标签」）。
