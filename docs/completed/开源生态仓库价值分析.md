# 开源生态仓库价值分析（Trae / Buddy 分类）

> 版本：v1.0 | 日期：2026-09-10 | 状态：调研结论
> 分析范围：用户指定的 28 个仓库 + 调研中发现的 5 个高关联新仓库
> 判定基准：本项目（AI Work 助手 v3.2.7）已实现能力 + `workbuddy-product-design.md`（F-01~F-60 已规划）+ `product-optimization-backlog.md`（E1/E2/W-01 等待办）
> 关联文档：`doubao-api-feasibility.md`、`tech-framework.md`

## 1. 结论概览

| 分级 | 定义 | 数量 |
|---|---|---|
| ⭐⭐⭐ 高价值 | 本项目未覆盖、对当前开发批次或已论证待办（W-01/E1/E2/F-38/F-43）有直接参照价值 | 8 |
| ⭐⭐ 中价值 | 有可借鉴的局部设计/避坑情报 | 8 |
| ⭐ 低价值 | 与本项目已实现能力重叠，或仅文档/清单类 | 15+ |

**三个最重要的发现**：

1. **`lovingfish/workbuddy-cliproxy` 是 Buddy 网关联调的避坑金矿**：上游 code 11101 拒绝非流式、腾讯内容审核对 Claude Code 固定 system 模板句的**精确匹配黑名单**及最小改写绕过、hy3 系列强制 `reasoning_effort=high`——这些是踩过坑才能得到的协议情报，直接补强蓝本 §5.5「网关上游协议要点」。
2. **`hailinzhao/antigravity-tools`（Antigravity-Manager）与本项目同技术栈（Tauri 2 + React + Rust/axum）且是同类产品**，其会话粘性指纹、P2C 负载均衡、账号状态机、分级重试、四段模型路由管线是网关调度层的最佳工程参照。
3. **W-01（Work 积分接入网关）的直接代码参照确认**：`Ttungx/trae-solo-local-api` 与 `Sliverkiss/traework2api` 均包装同一通道 `llm_utils_chat + function=solo_work_lite`，W-01 从"方案已论证"进入"有实现可抄"阶段。

## 2. Buddy 生态（WorkBuddy / CodeBuddy）

### 2.1 ⭐⭐⭐ 高价值

#### V-B1 · lovingfish/workbuddy-cliproxy —— 上游协议避坑情报（最高优先）
CodeBuddy 转 OpenAI/Anthropic 的 CLIProxyAPI 插件（.so/.dylib/.dll，clean-room 重写自 Sliverkiss/cpa-plugin）。

| 价值点 | 详情 | 对本项目意义 |
|---|---|---|
| 非流式被上游拒绝 | CodeBuddy 上游返回 **code 11101** 拒绝非流式请求，插件统一"内部转流式再聚合" | 补充蓝本 §5.5 联调避坑清单；网关 doubao/CodeBuddy 上游应默认流式+本地聚合 |
| **内容审核黑名单精确匹配** | 腾讯审核把 Claude Code 两句固定 system 模板逐字入黑名单（`You are Claude Code, Anthropic's official CLI for Claude.` / `Main branch (you will usually use this for PRs)`），命中即"敏感内容"拒答；**任何一字改动即绕过**。插件用 `sanitizeBlockedTemplates` 做最小改写（CLI→CLI tool、Main branch→Default branch） | 网关做 Claude Code 兼容层时的关键预处理；属于 cat-and-mouse，需可热更新的模板句映射表 |
| 思考模式强制 | hy3 系列只有 `reasoning_effort=high` 真正生效（medium/max/xhigh 被忽略），插件强制覆盖 | 模型目录策略：按模型族硬编码思考参数映射（补 §5.6） |
| prompt cache 陷阱 | Issue #4：字节一致请求 `prompt_cache_hit_tokens` 恒 0——上游缓存对代理流量不生效，按冷启动全价计费 | 积分成本模型需按"无缓存"估算；用量统计不要期待缓存命中字段 |
| 扫码登录 + token 刷新 | 凭据落 `workbuddy.json`，CPA 面板扫码 | M3 凭证续期的另一种交互形态（QR 登录）参考 |

#### V-B2 · hailinzhao/antigravity-tools（Antigravity-Manager）—— 同栈同类产品，调度层工程参照
Rust + Tauri 2 + React 19 + Zustand + axum 的多账号 Gemini/Claude 网关（对应仓库 lbjlaq/porsen/Antigravity-Manager）。**与本项目技术选型完全一致，相当于一份"平行实现答案"**。

| 价值点 | 详情 | 对本项目意义 |
|---|---|---|
| 会话粘性指纹 | 对**前 3 条消息内容做 SHA256** 生成 6 位会话 ID + 60s 时间窗锁定，同一会话恒落同一账号；宣称 prompt cache 命中率 +300% | 现有网关账号池调度可升级：会话粘性 → 上游缓存生效 → 积分节省（W-01/V-G1 联动） |
| P2C 负载均衡 | Power-of-Two-Choices 随机选二取优，比轮询/加权随机延迟更低 | 现有三因子/积分感知调度可对比吸收 |
| 账号状态机 | Available / QuotaProtection（配额<阈值剔除）/ RateLimited（429 指数退避自动过期）/ Forbidden（403 需人工）/ ProxyDisabled | 网关账号池状态机补全（本项目目前主要是冷却/禁用二元态） |
| 分级重试策略 | 429→解析 Retry-After，否则线性退避（1/2/3s）；503/529→指数退避；400+thinking.signature→固定 200ms 重试；其余→换号 | 统一重试策略表，直接可移植 |
| 四段模型路由管线 | 别名静态映射 → 用户自定义正则 → 系列通配（claude-sonnet-*→gemini-*-pro）→ 后缀检测（-thinking/-quality 注入参数） | 未来"任意模型名 → 上游真实模型"路由的成熟设计 |
| 协议细节 | 连续同角色消息自动合并（Gemini 要求交替）；单端口三协议靠 `anthropic-version` 头/路径区分；后台任务（生成标题/摘要）识别降级 | OpenAI→Anthropic/豆包转换层的既有坑位清单 |
| 运营细节 | 403 封禁检测自动标注账号、OAuth 预生成授权链接、V1→V2 数据热迁移 | 账号管理 UX 参考 |

#### V-B3 · Sliverkiss/workbuddy2api —— 调度与运维细节二次借鉴
协议层参考已在蓝本 §7.2 吸收（**判定：主协议已做**）。本轮补充确认的高价值细节：

- **三因子加权随机选号**：credits × 闲置时长 × 成功率，+ 100ms 防惊群窗口——比纯积分感知调度更均衡，可并入批次 2 调度增强。
- **流式 tool_calls 按 index 合并**、非流式本地聚合——OpenAI tools 透传的标准实现。
- `/healthz` 无健康账号返回 503（可接 LB）、`/status` 全账号画像、请求级 TTFB 日志表——运维可观测性模板。
- 双时段签到（09:00/21:00）+ **积分耗尽账号次日 04:00 自动恢复重试**——M4 签到排程的可借鉴策略。

#### V-T3 · connectedGraph/trae2api-web —— 多账号池管理面板参照（2026-08 新，164★ 活跃）
Go 反代（端口 7864），OpenAI 兼容 + 内置 Web 管理台。

- **账号池运维全活**：凭据 `auths/` 目录 + 池状态 `data/state.json` 持久化、导入/软启停/昵称/Web 登录流、按积分余量轮转。
- **错误码分级冷却**：1005 / 429 / 401 / 5xx 分别处理 + 故障轮转；每日定时签到 + **token 过期前主动刷新**（比"过期后刷新"更稳）。
- `TW2A_API_KEY` 保护写操作与管理台。
- 对本项目意义：M2 账号管理 + 网关账号池的 UX 与状态持久化参照；"token 过期前主动刷新"建议纳入 M3 凭证续期设计。

#### V-T4 · muskke/trae-api-proxy —— Responses API 与服务端搜索代执行（2026-09 活跃）
Go 单账号零第三方依赖，v0.5.1。

- **Codex 兼容层**：`/v1/responses` 全支持，Codex 发 `type:"web_search"` 时**代理侧代执行搜索/页面读取、结果回喂 Trae、按原生 `web_search_call` 事件返回**——"上游不支持的工具调用在代理侧补齐"的完整范式，对网关工具调用增强（M6/M7）有直接参考价值。
- 抓包 header 环境变量注入（APP_ID/DEVICE_ID/IDE_VERSION 等）模式——与本项目 MITM 采样思路一致。
