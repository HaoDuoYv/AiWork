## 二、E-01 豆包对话网关——模型分析与 OpenAI 兼容设计

### 2.1 豆包 Web 对话模型分析

豆包 Web 端不是"多模型选择"形态，而是**单助手 + 模式开关**形态。上游事实（tech-framework 附录 C + doubao2api 情报）：

1. **对话端点**：`POST https://www.doubao.com/samantha/chat/completion`（SSE 响应）。
2. **三模式**：`doubao`（快速）/ `doubao-think`（思考）/ `doubao-expert`（专家/Agent）。请求体规格（2026-09 doubao2api 深度复核固化，见 §8.1）：`messages[0].content` 为 JSON 字符串 `"{\"text\":\"...\"}"` + `content_type=2001`；`completion_option` 真实字段组（`use_deep_think` / `use_auto_cot` / `launch_stage` / `memory_type` 等），三模式 = `use_deep_think:false` / `:true` / `:true+use_auto_cot:true`（三模式共用同一底层 Seed 模型，专家模式仅注入 CoT 提示）。网关侧**对外呈现为三个独立模型名**，这是 OpenAI 兼容面最自然的投影——用户选模型 = 选模式，网关内部映射到对应 `completion_option`。
3. **多轮对话**：豆包以 `conversation_id` 组织会话（服务端持有上下文）。OpenAI 请求是无状态 messages 数组，需做**会话桥接**：
   - **主路径（conversation_id 映射表）**：请求带 `conversation_id` 扩展字段（或经 sticky 指纹命中映射）→ 直接续聊；客户端发 `/clear` 类信号或映射不存在时新建。
   - **兜底路径（消息合并）**：无法关联映射时，把 messages 全量合并为单条 user 消息（参考 `wb_payload.rs` 同角色合并先例），每轮全量重述。豆包上游对长 prompt 宽容，此路径保证**无状态客户端也能正确多轮**，代价是 token 浪费（豆包免费额度下可接受）。
4. **思考链**：SSE 思考事件 → OpenAI `delta.reasoning_content`（`Tom6814/WorkBuddy2API` 同款透传形态，WB 侧已验证客户端兼容性）。
5. **多模态入口 bot**：多模态对话走专用 `bot_id 7338286299411103781`（生图/生视频/识图路由），E-03 详述。
6. **风控形态：验证码墙而非拒绝服务**——错误码矩阵（签名决策的输入）：

| 码 | 语义 | 网关处置 |
|---|---|---|
| `710012001` | sessionid 吊销 | 复用探活逻辑标记失效，账号停止调度（对齐 `doubao_session.rs` 既有判定） |
| `710022004` | 需要验证码（人机墙） | 账号冷却 + 记 `needs_captcha` 状态（人工过验证码后自动恢复）；不换号重试（同池其他账号大概率同状态，防连锁触发） |
| `712010702` | Cookie/设备指纹缺失或编码错误 | 本地构造问题（`doubao_chats.rs` 已实证 ttwid/sid_guard 需 URL 编码）→ RetrySame 修参重试一次，再失败 Fatal + 告警 |
| HTTP 200 无数据流 | 上游静默吞掉（签名被拒的典型形态） | 计入连续失败退避升级（复用 `err_count≥3` 熔断 30m×2^trips） |

### 2.2 模型目录（/v1/models 聚合）

```text
doubao            快速模式（默认）
doubao-think      思考模式（带 reasoning_content）
doubao-expert     专家/Agent 模式（completion_option agent 组）
doubao-vision     多模态识图（E-03，需 TOS 上传，bot 路由）
doubao-image      生图（E-03）
doubao-video      生视频（E-03，异步）
doubao-music      音乐（E-03，慢同步）
```

命名原则：全部 `doubao-*` 前缀，与 `unified_catalog.rs` 的 `canonical_id` 归并不冲突（豆包模型名不会与 Trae/Buddy 撞名），目录声明能力字段（`supports_image` 等）对齐 WB 侧语义——**能力声明永远读真实能力，勿硬编码**。

### 2.3 新增 provider 的架构落点（六处改动点）

按 1.2 节探索结论，新增 doubao provider 的全部改动点：

```rust
// PoolEntry 增字段
pub struct PoolEntry {
    // ...既有字段不动...
    pub doubao: Option<DoubaoCreds>,   // Some = 豆包账号
}
```

对照 `wb_upstream.rs` 的三铁律形态，豆包侧铁律（`doubao_chats.rs` / `doubao_quota.rs` 实证 + doubao2api 情报）：

payload 构造（`doubao_payload.rs`）：OpenAI messages → 豆包体（`content` + `conversation_id` + `completion_option` 模式组 + `bot_id`）；多轮合并逻辑参照 `wb_payload.rs` 四坑清单形态，豆包侧已知坑（批次 0 固化后补充）：非流式拒绝、SSE 事件序列形态、`msg_id` 递增语义。

### 2.5 SSE 转换（doubao_sse.rs）

豆包 SSE 是**事件块**形态（`event_type` 枚举分派 + `event_data` 双层序列化），与 OpenAI delta 流不同，需一次投影。event_type 真实枚举（doubao2api 固化）：`1=HEARTBEAT / 2001=CMPL / 2002=ACK（含 conversation_id）/ 2003=FIN / 2004=CMD / 2005=ERR / 2010=VERBOSE`；文本/思考增量在 CMPL 内按 `content_type` 区分（10000 主回答 / 2008 思考链 / 2074 生图）；用量口径 `message.ext.input_tokens/output_tokens`：

```rust
pub enum DoubaoEvent {
    MessageDelta { content: Option<String>, reasoning: Option<String>, },
    ImageBlock(Vec<Creation>),        // block_type=2074，E-03 生图
    AsyncTask { task_id: String },    // fin_reason.async_task.id，E-03 生视频
    Done { conversation_id: String, msg_id: String, usage: Option<DoubaoUsage> },
    RiskHit { code: String },         // 710022004 等
}

// 投影：MessageDelta → OpenAI chunk（content / reasoning_content）
// Done → [DONE]，同时更新 conversation 映射表与 usage 记账
```

聚合模式（非流式客户端）直接复用 `wb_sse.rs::aggregate` 的 tool_calls 合并思路（豆包无 tool_calls，更简单——只拼 content/reasoning）。

### 2.6 会话映射表与粘性

```rust
/// 映射键优先级：显式 conversation_id 扩展字段 > sticky 指纹（前3消息 hash，60s~10min TTL）
/// > messages 合并兜底
pub struct DoubaoConv {
    pub conversation_id: String,   // 豆包侧会话
    pub msg_id: String,            // 上游递增游标
    pub uid: String,               // 绑定账号（会话与账号强绑定，换号=新会话）
    pub updated_at: i64,
}
```

粘性语义对齐 F-77 结论：**粘住账号 = 豆包服务端上下文命中（等价上游 KV cache），换号必然丢上下文**——豆包池的粘性 TTL 应长于 WB 池（建议默认 10min），busy 让位仅当映射不存在（新会话）时生效。

## 三、E-02 指纹嗅探持久化 + a_bogus 纯算法生成器

### 3.1 嗅探扩展（device_proxy/handler.rs）

现有豆包嗅探（sessionid/sid_guard/ttwid，handler.rs:641-729）扩展为**指纹嗅探**，同一处代码路径增补：

| 目标 | 采集位置 | 落库 |
|---|---|---|
| `msToken` | URL query（`/samantha/*` 请求）+ Cookie 双处；**query 处新鲜度最高**（Cookie 里的可能是旧的） | 按账号维度 |
| `passport_csrf_token` | Cookie / Set-Cookie | 按账号 |
| `device_id` / `web_id` / `tea_uuid` | URL query 固定参数（`doubao_chats.rs:26-40` 同款 19 位指纹）+ 抓包日志 | 按账号，**静态化**（同账号后续请求覆盖合并而非替换，保持稳定） |
| FAKE_HEADERS 采样 | `/samantha/chat/completion` 请求头全量快照（UA / Referer / Origin / sec-ch-ua 等） | 全局一份 + 时间戳（E-01 启动加载） |

存储：`store/schema.rs` 增行文档表 **`doubao_fingerprint`**（pk = uid，data = `DoubaoFingerprint` JSON，含 `captured_at` 新鲜度）——与 `doubao_accounts` 分表但同库，账号页联查展示"指纹新鲜度"徽标，无指纹账号标记"未经代理采集"。不采用 E-02 原文提出的 kv 方案（`doubao_captured_credentials` 是单账号快照语义，指纹需要按账号多行）。

嗅探触发条件：仅对 `*.doubao.com` 且路径命中 `/samantha|/alice|/im/` 的请求做指纹提取（避免全量 body 扫描开销）；`local_capture.rs` 同步加豆包分支兜底（读 Local State 的 `x-tt-multi-sids` 已有先例，`doubao_session.rs:219-250`）。

### 3.2 a_bogus 纯算法生成器（doubao_abogus.rs）

**关键边界**（附录 C）：a_bogus 绑定单次请求（query + UA + 时间戳嵌入签名体），嗅探只能固定 payload 短窗重放——**必须纯算法生成**。

Rust 移植三件套（约 300 行，不引入新 crate）：

| 组件 | 规格 | 移植来源 |
|---|---|---|
| SM3 哈希 | 国标 GB/T 32905，双哈希用法（两次摘要串联） | `abogus.py`（Evil0ctal 仓库）learn-the-design 重写；SM3 纯 Rust 实现约 120 行 |
| RC4 | 固定 keystream（密钥来自签名上下文） | 同上，约 40 行 |
| s4 自定义 base64 | 字符表与位序自定义（非标准 base64），输出 192 字符 | 同上 + `mafqla/douyin-api` 192 字符结构逆向文档 |

```rust
/// 生成 192 字符 a_bogus。输入三要素：
/// - query: 含 msToken 的完整请求 query 串
/// - ua:    与请求实际发出的 User-Agent 完全一致（不一致 = 签名失效）
/// - ts:    毫秒时间戳（嵌入签名体）
pub fn gen_a_bogus(query: &str, ua: &str, ts: i64) -> String {
    let body = build_sign_body(query, ua, ts);        // 固定结构拼接 + 随机 salt 2 字节
    let h = sm3_double(&body);                        // SM3 双哈希
    let enc = rc4_fixed_keystream(&h, &KEY_FROM_UA);  // RC4
    s4_b64_encode(&enc)                               // 自定义 base64 → 192 字符
}
```

**单测策略**：批次 0 的黄金样本（真实请求的 query+UA+时间戳+真实 a_bogus）做同参同 UA 输出比对——这是唯一可信的验收标准，比"移植代码看起来对"强得多。

**合规注意**：`abogus.py` 所在仓库许可（GPL/Apache）与本项目不同——只 learn-the-design（读懂算法规格：常量表、位运算流程），**代码全部自写**，不复制源文件。

### 3.3 批次 0 探测实验（0.5~1 天，先决）

用 Python（项目已有旁路先例）对黄金样本重放四档签名组合，产出**风控容忍矩阵**：

| 档位 | msToken | a_bogus | 预期 |
|---|---|---|---|
| A 随机/缺省 | 随机 | 缺省 | doubao-free-api 时代策略，2026 大概率拒（对照组） |

### 3.4 指纹生命周期管理

- **新鲜度告警**：`fingerprint_at` 超过 N 天（建议 7 天）且账号处于调度候选 → 池状态页黄标；建议打开代理刷一次豆包即自动刷新。

- **与探活联动**：`doubao_session.rs` 探活失败（710012001）→ `expired=true` 停止调度，已有逻辑；新增 710022004 → `needs_captcha=true` + 软冷却（`until`），探活通过后清除。

## 四、E-03 多模态资源化——独立接口 + 异步化 + 统一路由

### 4.1 对外接口设计（网关新增端点）

| 端点 | 形态 | 上游 | 同步/异步 |
|---|---|---|---|
| `POST /v1/images/generations` | OpenAI images 兼容 | **按模型路由**：`doubao-image` → 豆包；其余（supports_image 的 WB 模型）→ `wb_images.rs` 既有投影 | 同步（豆包侧 30~90s SSE 等待，网关内聚为同步响应；超时转任务查询） |
| `POST /v1/videos/generations` | 自定义（豆包独占，OpenAI 无对应标准） | 豆包 `content_type=2020` 两步异步 | **异步**：POST 返回 `{task_id}`；`GET /v1/videos/{task_id}` 轮询状态与结果 URL |
| `POST /v1/audio/music`（暂定名） | 自定义 | 豆包音乐（同端点同步 30~60s） | 同步 |
| `POST /v1/files` | OpenAI files 形态 | 豆包 TOS 上传 | 同步，返回永久 URI |
| `GET /v1/files/{id}` | 元数据查询 | 本地任务表 | 同步 |

设计决策：**生图统一入口、按模型路由**（一个 `/v1/images/generations`，模型名决定落豆包还是落 WB——对客户端最简单，也符合 `unified_catalog.rs` 的聚合哲学）；**生视频/文件中转站不做 OpenAI 兼容伪装**（标准里没有对应语义，硬套反而误导），用清晰的独立接口 + 明示文档。用户诉求"暴露独立接口和异步化"即此落地。

### 4.2 生图（doubao_image）

上游链路：`/samantha/chat/completion` + 多模态 `bot_id 7338286299411103781`，意图路由 → SSE `block_type=2074` 的 `creations[]`：

- `image.status == 2` = 完成；URL 优先级 `image_ori > image_raw > thumb`（**image_ori 通常无水印**——仅指获取平台自有原图，已烘焙水印不做去除，backlog §四红线）。
- **漏图兜底**：SSE 结束仍无完成图 → 轮询 `/message_node_info`（按 conversation_id + msg_id）拉取（`Jackchaos2025/Doubao-Image-Proxy` 成熟形态）。
- 图生图：请求带参考图时先走 TOS 上传得 `ref_image_key` 再入 prompt。
- ⚠ **水印事实修正（doubao2api 实证）**：所有返回图片 URL 均带 CDN ImageX tplv 模板渲染水印，**无法绕过**——`image_ori` 仅为平台自有原图 URL（相对 thumb 更大更清晰），并非"无水印"；已烘焙水印属图像内容，网关不做去除（backlog §四红线不变，但预期需修正）。
- 响应归一为 OpenAI images 格式：`{ data: [{ url, revised_prompt? }] }`；`b64_json` 不支持（豆包回 URL），明示。

### 4.3 生视频（doubao_video）——两步异步 + 断线重连

1. **下发**：`POST /samantha/chat/completion`，prompt 带 `content_type=2020` → SSE 返回 `fin_reason.async_task.id`（秒级返回，立即记入任务桥，状态 Running）。
2. **等待**：`GET /samantha/chat/async/stream`（SSE 长连接）等 `2021` 完成事件，**1~3 分钟**——网关不挂长连接干等：任务桥后台线程池逐任务持连接（受账号级并发上限约束，F-77 inflight 天然管控），客户端轮询 `GET /v1/videos/{task_id}`。
3. **断线重连**：async stream 断开后用 `event_id` 游标重连续传（不重复消费已完成事件）；死线超时标记 Failed(timeout)。

### 4.4 文件中转站（doubao_files）

- 上传：豆包 TOS 通道 ≤1GB，得**永久 URI**（免费跨机文件通道，顺带收益）。
- `POST /v1/files` multipart → 网关流式转发 TOS（不落盘缓存全文，≤1GB 体量网关不中转存储）→ 返回 `{id, uri, bytes, filename}`。
- 附带收益：识图/文档理解（60+ 格式）先 `files` 上传得 URI 再入 vision 对话——`doubao-vision` 模型的输入前处理即此通道。

### 4.5 统一资源 API 的能力矩阵落点

`/v1/models` 聚合输出每模型带能力声明（对齐 `unified_catalog.rs` 既有 `sources` 结构）：

```json
{
  "id": "doubao-image",
  "sources": [{ "pool": "doubao", "rate": 0, "enabled": true }],
  "capabilities": { "image_generation": true, "async": false }
}
```

客户端侧即可编程发现"谁能生图/谁异步"，这是"统一资源提供 API 服务"的可查询形态。

### 8.1 `wangchuxiaoji-oss/doubao2api`（Apache-2.0）——协议事实权威来源

**核心机制**：Playwright 在真实浏览器内执行 `fetch()`，字节前端 JS hook 自动注入 `a_bogus` + `msToken`——签名上下文与浏览器完全一致从而规避 `710022004`。**我们不采用 Playwright 路线**（重运行时 + 30~60s 冷启动 + 内存占用高），但它是本设计最丰富的协议事实源。

**可提取的协议事实（已逐条对照修正实现）**：

### 8.2 `amxsa/douyin_abogus_python`（abogus.py）——a_bogus 纯算规格

**核心机制**：bdms SDK V1.0.1.19 的纯 Python 复现（`sm3` 嵌套双哈希 + 魔改 RC4 + 5 张自定义 base64 表），是全部公开实现中结构最完整的算法规格来源（Evil0ctal 仓库该文件已 404 迁移；CSDN 逆向文章为 JSVMP 黑盒路线，无算法内部细节）。

**算法规格事实（据此重写了 `doubao_abogus.rs` 装配层）**：

```text
string_1 = 12B 随机段（list_1+2+3，random_list 掩码 0xAA/0x55 交织；
          list_1 的 g 位 = 45&0xAA=40）
string_2 = RC4(key="y") 加密的 [44B 定长头 + browser_code + 1B XOR 校验]
44B 头   = K 常量(44/24/239/14/3/1/1) + start/end 毫秒时间戳字节
           + params_code[21][22]（sm3²(urlencode(params)+"cus")）
           + method_code[21][22]（sm3²(method+"cus")）
           + ua_code[23][24]（sm3(s3表(rc4(ua, key="\x00\x01\x0e")))）
           + browser_len
output   = s4 表自定义 base64（3B→4C，移位 18/12/6/0，'=' 补齐）→ ~152-160 浮动
字符表   s4 = Dkdpgh2ZmsQB80/MfvV36XI1R45-WUAlEixNLwoqYTOPuzKFjJnry79HbGcaStCe
         s3 = ckdp1h4ZKsUB80/Mfvw36XIgR25+WQAlEi7NLboqYTOPuzmFjJnryx9HVGDaStCe
```

**对本项目的修正价值**：初版按错误记忆实现（整体 SM3 双哈希 + salt/query/UA/ts 拼接 + 固定 192 输出 + 自造字符表）——三算法原语（SM3/RC4）正确且经国标/RFC 向量验证，装配层已全部重写为上述规格。**合规注意**：仅按结构规格重写，未复制代码（该仓库 MIT，但坚持 write-our-own-code）。

### 8.3 `Jackchaos2025/Doubao-Image-Proxy`（MIT）——生图 SSE 解析范式

**核心机制**：Node.js 最小服务，`.env` 手工抓包（COOKIE/X_MS_TOKEN/DEVICE_ID/TEA_UUID/WEB_ID/MS_TOKEN/A_BOUGUS/ROOM_ID）→ 转豆包官方 chat payload → SSE 解析。

**可提取事实**：① 生图结果在 **`content_type 2074`**（非 block_type 口径——实现已做双兼容）；② `creations[]` 内 `image.status === 2` = 完成；③ URL 优先级 `image_ori > image_raw > thumb`（原图 → 原始 → 缩略）；④ **message_node_info 兜底最多 5 次**（实现取 6×5s，同量级）；⑤ 排障结论："刷 2001 但无 status=2 = Cookie/Token 过期"——与我们指纹/凭证分离存储的设计互证。其手工抓包形态被我们的 MITM 自动嗅探（E-02）整体替代。

### 8.4 `lzA6/doubao-2api`——多账号工程组织参照

**核心机制**：FastAPI + Playwright + stealth，`DOUBAO_COOKIE_{N}` 环境变量多账号 → CredentialManager 轮询 → `window.byted_acrawler.frontierSign()` 页内签名 → httpx 转发。

**对本项目的参照与超越**：

- **指纹静态化**：其"静态设备指纹"是已实现特性 ↔ 我们以 `doubao_fingerprint` 表 + 合并不替换红线落库，且重启不丢（其固化在 Playwright 实例内）；
- **其公开承认的三大局限恰是我们已交付的**：① Cookie 失效无自动处理（我们有 710012001→SessionDead + 探活续期）；② 纯 Python 签名为其"最高优先级重构目标"（我们 E-02 直接纯算落地）；③ 内存占用高/冷启动 30~60s（我们零浏览器依赖）。
- **待借鉴**：其 SessionManager 的有状态会话 ↔ 我们的 DoubaoConv 映射表（已实现，TTL 10min）。
